AdministrateMe V3 — platform architecture

Everything a member owns flows into one queue. Nothing leaves it undecided. Every decision can leave a rule behind, and the rules are why it converges.

The learning loop — where policy is written The human gate — nothing leaves undecided The model — drafts one object, decides nothing Written out — idempotent, undoable Refusal — an invariant with a test behind it

One mechanism, two moments

The New Connection Wizard is zeroing run against the past.
Zeroing is the wizard run against the present.

Same grouping component, same four dispositions, same rules table, two entry points. This is invariant I-6, and it is the highest-leverage constraint in the repo — building two grouping UIs or a second policy store produces two things that drift apart and a user who cannot predict either one.

The extraction contract — the entire AI surface

{
  "kind":  "calendar" | "reminder" | "file" | "drop",
  "title": "Flight DL2411 to Vancouver",
  "when":  "2026-08-28T06:15:00-04:00",
  "list":  "Personal",
  "why":   "Delta confirmation with a departure time",
  "sure":  true
}

One call, one object per item. Anything else and the item goes to triage undrafted — which is exactly what you do today, so the floor is "no worse than manual." Model-side learning from your dispositions is explicitly rejected: it produces behaviour you cannot name, audit, or revert. Learning happens by writing a rule you can see and switch off.

The nine invariants

Each has a test that fails when it is violated, written before the code that satisfies it. If a change makes one fail, the change is wrong — not the test.

#Invariant
I-1An item disposed of once never requires the same decision twice. A re-arriving external id matches its prior disposition.
I-2A connection with no wizard_completed_at may not produce items. Policy exists before volume.
I-3The model may never invent a date. No time in the source means when is null and it cannot be a calendar entry.
I-4decisions is append-only. No update, no delete, ever, including in migrations.
I-5Every automatic disposal is logged with its rule id and is undoable. Silent suppression is rejected.
I-6Wizard and zeroing write to the same rules table. A second policy store is rejected.
I-7A member may not read another member's items. Destinations are shared; inboxes are not.
I-8Finance proposes patterns, never transactions. Minimum three occurrences with a recognisable cadence.
I-9A push carries an idempotency key. A re-run cannot duplicate; an undo can always find its target.

What is deliberately not built

Knowledge graph engine · context engine · People directory · confidence classes · readiness states · source accounting · Comms surface · Scoreboard · observation mode as a separate mode · cross-member browsing · a forwarding inbox. Each was considered and rejected for a reason recorded in CONFLICTS-RESOLVED.md or docs/PRESENTATION.html. Read those before proposing one — it is probably in there with an argument attached.
